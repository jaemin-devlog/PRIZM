PRIZM P7-A v2 합성 포트폴리오 — SYN2-U02
OrbitMosaic: 위성 영상 배치의 대기, 품질 격리, 재처리

본 문서는 검색 일반화 평가를 위해 만든 합성 데이터다. 실제 위성 사업자·기관·촬영 자료와 관련이 없다.

[실험 노트 A — 입력 계약]
OrbitMosaic는 촬영 궤도별 GeoTIFF를 받아 구름 마스크와 좌표계를 확인하고 일 단위 모자이크를 생성했다. 외부 제공자는 FastAPI endpoint에 manifest를 등록했다. API는 scene_id, revision, orbit, checksum, object URI를 검증하고 job key를 반환했다. 실제 영상 파일은 API 서버를 통과하지 않았고 object storage에서 직접 읽었다.

[실험 노트 B — 기다리는 작업]
manifest가 먼저 도착하고 큰 영상 객체는 수분 뒤에 보이는 경우가 있었다. 초기 구현은 Airflow worker가 polling하면서 slot을 점유했다. 이를 deferrable operator로 바꿔 object-ready event가 올 때까지 triggerer가 기다리게 했다. 계산 worker는 파일이 준비된 작업에만 사용됐다. sequencer가 아니라 영상 제공자의 업로드 지연을 흡수하기 위한 설계였다.

[실험 노트 C — Spark 병목]
하루 입력은 최대 6.4TB였다. 촬영 건수가 적은 극지방 orbit과 수천 장이 몰리는 중위도 orbit의 partition 크기가 크게 달랐다. acquisition_date와 orbit을 1차 partition으로 두고 Spark adaptive query execution으로 skew partition을 다시 나눴다. 작은 중간 파일은 모자이크 완료 시점에 병합했다. 동일한 40-node 조건에서 end-to-end 처리 시간은 138분에서 41분으로 줄었다.

[실험 노트 D — 품질 격리]
8,750개 delivery package를 받은 검증 주간에 checksum 또는 TIFF directory가 손상된 GeoTIFF 64개를 찾았다. 해당 scene은 quarantine table과 별도 object prefix로 이동했다. 오류가 있는 package 전체를 버리지는 않았지만, 격리된 scene은 모자이크 계산과 공개 catalog에 들어갈 수 없었다. 운영자는 원본 checksum, 발견 단계, 재전송 ticket을 함께 확인했다.

[실험 노트 E — 과거 데이터 재적재]
Delta Lake MERGE key는 scene_id와 revision의 조합이었다. 같은 장면의 보정판은 새 revision으로 유지하고 동일 revision의 재전송은 update 없이 종료했다. 9,600,000개 scene metadata를 backfill한 검증에서 최종 active row 중복은 0건이었다. backfill job은 처리한 날짜 범위를 checkpoint table에 기록해 중단 지점부터 재개했다.

[실험 노트 F — 선택하지 않은 것]
Dask는 로컬 prototype으로 동일 변환 30개를 비교하는 데만 사용했다. 운영 scheduler와 분산 계산 엔진은 Airflow와 Spark를 유지했다. 외부 팀이 제공한 cloud mask model은 inference input으로 소비했지만, 객체 탐지나 cloud model을 직접 학습하지 않았다.

[실험 노트 G — 주변 업무]
CloudCal 보정 도구에서는 분석가가 작은 표본을 노트북에서 확인할 수 있도록 DuckDB export를 제공했다. 이 기능은 대규모 OrbitMosaic Spark 성능 수치에 포함하지 않았다. on-call 문서에는 object 지연, checksum 오류, Spark executor 손실을 서로 다른 복구 절차로 나눴다.

[결론]
배치 시간을 줄인 것만으로는 성공이 아니었다. 준비되지 않은 객체는 계산 자원을 점유하지 않아야 했고, 손상 scene은 공개 결과에 섞이지 않아야 했으며, 수백만 건 재처리는 revision 의미를 보존해야 했다. 세 경계를 독립적으로 검증한 뒤에만 41분 결과를 성과로 기록했다.
