PRIZM P7-A v2 합성 포트폴리오 — SYN2-U04
ScoreRights Catalog: 저작권 자료 수집과 검색 인덱스 교체

이 문서는 가상의 음악 권리 관리 제품을 설명하는 평가 자산이다. 실제 창작자, 음원, 계약 또는 정산 정보는 없다.

[2025-01 — 서로 다른 식별자]
ScoreRights Catalog는 출판사와 유통사에서 받은 work, recording, contract 자료를 연결했다. 같은 곡이 제목 표기만 달라 여러 번 들어오는 문제가 있었다. NestJS ingestion API는 ISWC와 ISRC를 형식별로 정규화하고 source organization을 함께 저장했다. 식별자가 없는 오래된 자료는 자동 병합하지 않고 review queue로 보냈다.

[2025-03 — 원본과 파생물]
계약 PDF와 cue sheet 원본은 Cloudflare R2에 저장했다. upload content hash가 이미 존재하면 OCR과 metadata extraction job을 새로 만들지 않았다. 원본 object는 삭제하지 않았고, 파싱 규칙이 바뀌면 같은 원본에서 새 extraction version을 만들었다. 비동기 작업은 Cloudflare Queues로 전달했으며 consumer는 extraction key를 기준으로 멱등 처리했다.

[2025-05 — 검색 구조]
2,300,000개 work record를 Meilisearch에 색인했다. 권리자 이름, 작품명, ISWC prefix, territory를 filterable attribute로 구분했다. 새 schema는 `rights-2025-05`, `rights-2025-08`처럼 별도 index로 만들고 sample query 검증 뒤 alias를 원자적으로 교체했다. 색인 구축 중에도 기존 index가 요청을 처리했다.

[2025-07 — 성능과 검증]
frequent-owner filter의 cardinality 문제를 줄이고 ranking rule 순서를 조정했다. 동일 20-query replay에서 검색 P95는 1.6초에서 240밀리초로 낮아졌다. alias 전환 14회 동안 빈 결과가 노출된 횟수는 0건이었다. 성능 수치는 warm replay 결과이며 첫 색인 build 시간과 섞지 않았다.

[2025-09 — 권리 충돌]
두 source가 같은 territory의 지분을 각각 100%로 주장하면 자동으로 한쪽을 선택하지 않았다. source priority, 계약 유효 기간, 수동 review 상태를 conflict record에 남겼다. 검색 결과는 미해결 충돌 배지를 보여줬지만 정산 비율을 임의로 계산하지 않았다.

[2025-10 — 정산 주변 기능]
SettleBoard export는 월별 18,600개 statement를 생성했다. 이 숫자는 검색 corpus 규모와 다른 업무 지표다. export는 catalog snapshot id를 기록해 어느 권리 상태로 계산했는지 재현 가능하게 했다.

[검토했지만 선택하지 않은 것]
Typesense를 50,000개 sample record로 비교했지만 production 검색 엔진으로 전환하지 않았다. 블록체인 기반 정산 원장은 제품 범위에 없었고 설계하거나 구현하지 않았다. 현재 추천 표시는 장르와 territory에 대한 규칙형 facet뿐이다.

[회고]
검색 속도보다 먼저 원본, 파생 extraction, 검색 index, conflict 상태의 버전을 분리해야 했다. content hash는 중복 작업을 줄였고 alias 교체는 검색 연속성을 지켰지만, 권리 충돌의 진실을 자동으로 결정하는 도구는 아니었다.
