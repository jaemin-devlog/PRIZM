# PRIZM 현재 구현 현황

> PRIZM은 개인의 커리어 문서를 모으고, 실제 경험과 원문 근거를 찾기 위한 문서 플랫폼으로 개발 중입니다.

## 한눈에 보기

현재 완성된 것은 커리어 분석 제품 전체가 아니라 다음 문서 처리 기반입니다.

```text
TXT 원본 등록
→ 안전한 파일 저장과 해시 기록
→ 비동기 청크·임베딩 처리
→ 활성 버전 전환
→ 자연어 의미 검색
```

아직 채용공고 분석, 경력 근거 카드나 지원 문서 생성 기능은 없습니다.

## 왜 이 기반을 먼저 만들었나

커리어 정보를 다루는 기능은 답변보다 근거가 먼저 있어야 합니다. PRIZM은 사용자가 실제로 등록한 자료를 보존하고, 검색 결과가 어느 문서의 어느 부분에서 왔는지 되돌아갈 수 있는 구조부터 만들었습니다.

AI는 등록 문서에 없는 경험, 기술, 성과나 수치를 만들어서는 안 됩니다. 검색에서 근거가 나오지 않을 때도 사용자의 주장이 거짓이라고 단정하는 것이 아니라, 현재 등록된 자료에서는 근거를 찾지 못했다는 의미로 다뤄야 합니다.

## 현재 동작하는 문서 흐름

### 1. TXT 등록

사용자가 TXT 파일을 올리면 다음 검사를 수행합니다.

- 빈 파일인지 확인
- TXT 확장자인지 확인
- 허용 크기 이내인지 확인
- 파일명으로 저장 경로를 조작하려는지 확인
- 파일 내용의 SHA-256 해시 계산

원본 파일은 서버가 만든 문서·버전 디렉터리에 저장하고, DB에는 문서와 버전 메타데이터를 기록합니다. 저장 직후 상태는 `QUARANTINED`입니다.

여기서 `QUARANTINED`는 사람의 승인을 기다린다는 뜻이 아닙니다. 파일 저장과 기본 검사는 끝났지만 아직 검색 벡터를 만들지 않은 업로드 초기 상태입니다.

### 2. 비동기 색인

Spring Scheduler Worker가 처리 작업을 선점하면 문서 버전을 `PROCESSING`으로 바꾸고 TXT를 청크로 나눕니다. 각 청크는 Ollama `bge-m3`로 1024개의 숫자로 이루어진 임베딩으로 변환됩니다.

Worker는 파일 읽기나 Ollama 호출 중 DB 행 잠금을 계속 잡고 있지 않습니다. 여러 Worker가 동시에 실행돼도 한 작업만 가져가도록 `SKIP LOCKED`를 사용하고, 중단된 Worker의 작업은 lease 만료 후 다시 회수합니다. `claim_version`은 회수되기 전의 Worker가 뒤늦게 결과를 덮어쓰는 것을 막습니다.

### 3. 활성화

모든 청크와 임베딩이 준비되면 한 DB 트랜잭션에서 다음을 함께 처리합니다.

```text
청크와 벡터 저장
→ 문서 버전 ACTIVE
→ documents.active_version_id 교체
→ 처리 작업 COMPLETED
```

중간에 실패하면 불완전한 청크를 검색에 노출하지 않습니다. 재시도 가능한 오류는 작업을 `RETRY_WAIT`로 바꾸고 1분, 5분, 15분 간격으로 최대 세 번 다시 시도합니다. 최종 실패한 버전은 `FAILED`가 됩니다.

### 4. 의미 검색

사용자의 질문도 같은 `bge-m3` 모델로 1024차원 벡터로 바꿉니다. PostgreSQL pgvector가 cosine 거리로 가장 가까운 청크를 찾습니다.

```text
사용자 질문
→ 질문 임베딩
→ ACTIVE이면서 active_version_id가 가리키는 청크만 검색
→ 실제 콘텐츠와 문서 출처 반환
```

`score = 1 - distance`는 검색 유사도이지 정답 확률이나 경력 사실의 정확도가 아닙니다. 현재 생성형 AI 답변은 만들지 않습니다.

## 현재 인증과 역할

- 비밀번호는 BCrypt 해시로 저장합니다.
- 로그인하면 만료 시간이 있는 JWT Access Token을 발급합니다.
- 요청마다 DB의 현재 사용자 활성 상태, 이메일과 역할을 다시 확인합니다.
- 역할은 `USER`와 `SYSTEM_ADMIN`입니다.
- `SYSTEM_ADMIN`은 개인 문서의 승인자가 아닙니다.
- 개인 원본이나 검색 결과를 운영자가 조회하는 관리자 API는 없습니다.

현재는 사용자별 문서 소유권과 데이터 격리가 아직 없습니다. 따라서 다음 개발 단계에서 이 경계를 가장 먼저 추가해야 합니다.

## 현재 API

- `POST /api/auth/login`: 로그인
- `GET /api/users/me`: 현재 사용자 조회
- `POST /api/documents`: TXT 등록
- `GET /api/documents`: 문서 목록
- `GET /api/documents/{documentId}`: 문서·버전 상세
- `POST /api/search`: 활성 문서 청크 의미 검색
- `GET /actuator/health`: 상태 확인

원본 다운로드, 새 버전 업로드, 문서 삭제, 처리 작업 관리와 문서 승인 API는 아직 없습니다.

## 현재 기술 기반

- Java 17, Spring Boot 4.1
- React, TypeScript, Vite 초기 셸
- PostgreSQL 16, pgvector 0.8.2, Flyway
- Ollama `bge-m3`, 1024차원 임베딩
- Docker Compose와 Testcontainers 통합 테스트
- 로컬 원본 파일 저장소

프런트엔드는 실행 환경을 확인하는 초기 화면만 있고 로그인·업로드·검색 화면은 아직 없습니다.

## 아직 없는 기능

- 사용자별 문서 소유권과 격리
- PDF, DOCX, PPTX와 OCR
- 새 문서 버전 등록과 사용자 검토
- 커리어 문서 유형과 기술 태그 추출
- 경력 근거 카드
- 채용공고 등록과 요구사항 분석
- 근거 없는 주장 안내 기능
- 지원 패키지와 면접 질문 생성
- 생성형 답변과 MCP

OpenSQL 지정과제를 위한 프로필과 검증 Gate는 준비돼 있지만, 현재 실행 증거는 PostgreSQL 16과 pgvector 환경에 한정됩니다. 실제 OpenSQL, OpenProxy와 OpenHA는 아직 검증하지 않았습니다.

## 다음 개발 단계

다음 작업은 사용자별 문서 소유권과 데이터 격리입니다.

```text
문서를 등록한 사용자 기록
→ 목록·상세 조회 범위 제한
→ 벡터 검색 SQL에 사용자 경계 적용
→ 다른 사용자의 원본·청크·검색 결과 차단
```

이 경계를 검증한 뒤 문서 형식과 커리어 기능을 순서대로 확장합니다.

## 아주 간단한 결론

**지금까지:** TXT 원본을 저장하고, 장애 복구가 가능한 비동기 Worker로 임베딩한 뒤 활성 버전만 자연어 검색하는 기반을 만들었습니다.

**다음:** 사용자별 문서를 확실히 분리해 개인 커리어 자료를 다룰 수 있는 데이터 경계를 만듭니다.
