# AI 에이전트 작업 방식 선택과 적용 기준

## 목적과 범위

이 문서는 PRIZM을 개발할 때 사용하는 AI 에이전트의 작업 방식을 설명한다. 제품 기능,
API 계약, 대회 요구사항 또는 구현 완료 증거를 정의하는 문서가 아니다. 실제 구현 여부는
항상 source code, Flyway migration과 실행 가능한 test로 판단한다.

PRIZM의 규범 원본은 [AGENTS.md](../AGENTS.md)다. 이 문서는 그 절차를 바꾸지 않고,
AI가 작업 중 잘못된 가정을 하거나 요청 범위를 넓히는 문제를 줄이기 위한 보완 기준을
기록한다.

## 선택 배경

AI 에이전트는 짧은 요청을 받았을 때 다음과 같은 실수를 할 수 있다.

- 불확실한 요구사항을 임의로 해석한 뒤 구현을 계속한다.
- 현재 요구와 관계없는 추상화, 설정, 리팩터링을 함께 추가한다.
- 이미 존재하는 사용자 변경이나 인접한 코드·주석·형식을 정리한다.
- "동작할 것"이라고 판단하고, 성공 조건과 실제 검증을 분리하지 못한다.

PRIZM은 문서 버전의 원자적 활성화, 사용자 소유권 격리, 비동기 Worker의 lease와
claim-version fencing처럼 작은 수정도 데이터 정합성에 영향을 줄 수 있는 계약을
보존한다. 따라서 빠른 생성보다 범위·근거·검증을 먼저 확인하는 방식이 필요하다.

## 기존 작업 방식

기존 방식은 `AGENTS.md`의 다음 순서를 따른다.

```text
ORIENT -> SPEC -> PLAN -> IMPLEMENT -> VERIFY -> AUDIT -> INTEGRATE
```

| 단계 | 기존 방식에서 하는 일 |
|---|---|
| ORIENT | 문서·source·migration·test를 읽고 실제 상태와 위험을 확인한다. |
| SPEC / PLAN | 요구사항, 보존 계약, 변경 범위, 검증 조건을 정한다. |
| IMPLEMENT | 승인된 작은 수직 슬라이스만 구현하고 사용자 변경을 보존한다. |
| VERIFY | 필요한 단위·통합·환경 검증을 실제로 실행하고 `PASS`·`FAIL`·`NOT_RUN`을 구분한다. |
| AUDIT | 수정자와 분리된 관점에서 diff, 보안, 데이터 계약, 문서와 테스트를 검토한다. |
| INTEGRATE | 실제 PR·CI·병합 근거를 기록하고 임시 브랜치를 정리한다. |

이 방식은 **언제 무엇을 확인할지**를 잘 정의한다. 다만 한 단계 안에서 AI가 어떤
태도로 코드를 작성해야 하는지까지는 짧고 직접적인 질문으로 정리돼 있지 않았다.

## 추가한 AI 작업 원칙

개발 환경에는 Karpathy-inspired guidelines를 로컬 Codex skill로 설치했다. 이는
프로젝트 배포물에 포함되는 dependency나 PRIZM의 런타임 기능이 아니다. 원문의 문장을
저장소에 복사하지 않고, 다음 네 가지 행동 원칙만 프로젝트 상황에 맞춰 적용한다.

| 원칙 | PRIZM에서의 적용 |
|---|---|
| 코딩 전 사고 | 요구가 여러 방식으로 해석되거나 보안·데이터 계약을 바꿀 수 있으면 가정과 선택지를 먼저 밝힌다. |
| 단순성 우선 | 현재 요청을 해결하는 최소 변경을 선택한다. 단일 사용처를 위한 새 추상화나 미래 기능은 추가하지 않는다. |
| 외과적 변경 | 요청과 직접 관계없는 source, 주석, 포맷, 다른 사용자의 변경은 수정하지 않는다. 이번 변경이 만든 미사용 코드만 정리한다. |
| 목표 중심 실행 | 구현 전에 성공 조건과 검증 명령을 정하고, 실제 결과가 확인될 때만 완료로 기록한다. |

참고한 공개 지침은 [multica-ai/andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills)의
MIT 표기 `karpathy-guidelines` skill이다. 이 저장소에는 해당 skill 파일, Claude plugin,
모델 가중치 또는 외부 실행 파일을 포함하지 않는다.

## 기존 방식과 현재 방식의 차이

| 관점 | 기존 방식 | 현재 방식 |
|---|---|---|
| 요구 해석 | 관련 문서를 읽고 합리적 가정으로 진행할 수 있다. | 결과를 바꾸는 모호함은 가정·선택지·영향을 공개하고 필요한 경우 사용자 판단을 구한다. |
| 설계 | Spec과 Plan으로 범위를 관리한다. | Plan 안에서도 가장 작은 해결책을 먼저 비교하고, 요청되지 않은 확장성은 제외한다. |
| 수정 범위 | 관련 파일을 조사해 필요한 변경을 수행한다. | 각 변경 줄이 사용자 요청 또는 검증 실패와 직접 연결되는지 확인한다. |
| 정리 | 기존 사용자 변경을 보존한다. | 인접 코드의 개선·리팩터링은 발견만 보고한다. 이번 변경이 만든 미사용 항목만 제거한다. |
| 완료 판단 | 단계별 검증·감사 evidence를 남긴다. | 구현 전에 관찰 가능한 성공 조건을 문장으로 고정하고, 그 조건을 충족하는 실제 검증을 남긴다. |
| 작은 작업 | 전체 절차를 적용하면 과해질 수 있다. | 오타나 명백한 한 줄 수정에는 필요한 확인과 최소 검증만 적용한다. |

## 적용 예시

### 문서 상세 화면의 버튼 깨짐

기존 방식은 관련 React 컴포넌트와 CSS를 읽고 수정한 뒤 lint와 build를 실행한다.
현재 방식에서는 먼저 "상세 모달의 특정 버튼 문제인지, 공통 버튼 규칙 문제인지"를
확인한다. 공통 디자인 체계를 다시 설계하지 않고, API·문서 상태 계약은 바꾸지 않으며,
성공 조건을 "지정된 화면 너비에서 버튼 텍스트가 잘리지 않고 lint·build가 통과한다"로
정한다.

### 문서 삭제 처리 변경

"단순성"은 요청 트랜잭션 안에서 파일을 바로 삭제하라는 뜻이 아니다. PRIZM의 경우
파일시스템과 DB transaction은 하나의 원자적 transaction이 될 수 없으므로, durable
Cleanup Job과 재시도·복구 구조가 필요한 최소 설계다. 이처럼 기존 보존 계약이 요구하는
복구·보안·정합성 코드는 단순화를 이유로 제거하지 않는다.

## 이 방식의 문제점과 제한

| 위험 | 이유 | 대응 |
|---|---|---|
| 작업 속도 저하 | AI가 가정·선택지·성공 조건을 먼저 설명하면 단순 작업도 길어질 수 있다. | 영향이 작은 오타·명백한 수정에는 최소 확인만 적용한다. |
| 질문 과다 | 모든 모호함에 멈추면 에이전트가 자율적으로 진행하지 못한다. | 결과·보안·데이터·외부 상태를 바꾸는 모호함에만 질문한다. 그 외에는 가정을 공개하고 진행한다. |
| 과도한 단순화 | 짧은 코드가 항상 안전한 설계는 아니다. | 인증, 소유권, migration, 비동기 복구, 파일 삭제처럼 PRIZM이 보존하는 계약은 우선한다. |
| 테스트 만능주의 | test 통과만으로 OpenSQL·OpenHA·외부 서비스 호환성을 증명할 수 없다. | 필요한 환경을 실제 사용했는지 기록하고, 실행하지 않은 항목은 `NOT_RUN`으로 남긴다. |
| 지침의 강제력 부족 | 로컬 skill과 Markdown은 행동 지침일 뿐 기술적으로 명령을 차단하지 않는다. | CI, 코드 리뷰, 독립 AUDIT, 권한·sandbox 설정 같은 별도 통제를 계속 사용한다. |
| 개발 환경 차이 | 로컬 Codex skill은 설치한 컴퓨터에서만 동작하며 Git으로 공유되지 않는다. | 프로젝트 공통 규칙은 계속 `AGENTS.md`에만 기록한다. |

## 현재 적용 기준

1. `AGENTS.md`가 프로젝트 규칙의 단일 원본이다. 충돌하면 `AGENTS.md`와 사용자의 최신 지시를 따른다.
2. Karpathy-inspired 원칙은 구현·리뷰·리팩터링 시의 보조 판단 기준이다. 대회 공식 요구사항이나 구현 증거로 주장하지 않는다.
3. 새 기능, migration, 보안·소유권·비동기 처리 변경에는 기존 staged delivery workflow와 네 원칙을 함께 적용한다.
4. 문서 오타나 명백한 단일 수정에는 전체 Plan을 강제하지 않되, 변경 범위와 기본 검증은 남긴다.
5. 외부 환경 결과는 PostgreSQL, Docker, Ollama, OpenSQL, OpenProxy, OpenHA를 서로 대체하지 않고 각각 실제 실행 결과로 기록한다.

## 유지보수

이 문서는 AI 작업 방식의 선택 이유를 설명하는 기록이다. 실제 프로젝트 규칙이 바뀌면
먼저 `AGENTS.md`를 수정하고, 이 문서의 설명이 어긋나는 경우에만 함께 현행화한다.
