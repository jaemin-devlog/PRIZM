PRIZM P7-A v2 합성 포트폴리오 — SYN2-U01
QuarryFlow Dispatch: 계근소 재전송과 자재 배차 정합성

이 문서는 평가용 합성 사례다. 등장하는 인물, 회사, 현장, 수치와 사건은 모두 가상이며 실제 개인정보나 영업 정보를 포함하지 않는다.

[01. 배경]
QuarryFlow Dispatch는 골재·아스콘 주문을 28개 출하 거점에 배정하고, 현장 계근소에서 확정된 중량을 운송 전표로 만드는 시스템이다. 연간 처리량은 약 3,200,000개 전표였다. 주문 API 자체보다 어려운 부분은 현장 장비였다. 일부 계근 제어기는 통신이 끊기면 완료 callback을 로컬에 저장했다가 연결이 회복된 뒤 여러 번 전송했다. 같은 전표가 두 번 확정되면 재고와 운임 정산이 함께 어긋났다.

[02. 제약과 선택]
거점마다 취급 자재와 운송 규칙이 달랐고, 한 거점의 장비 장애가 다른 거점의 배차를 지연시키면 안 됐다. C#과 .NET 8로 작성한 접수 API는 요청을 짧게 끝내고 Azure Service Bus topic에 명령을 발행했다. subscription filter는 depot code와 material class를 기준으로 구성했다. 이 방식으로 각 worker는 자신이 담당하는 거점·자재 메시지만 받았고, 새로운 거점 추가 때 API 배포가 필요하지 않았다.

Solace PubSub+도 후보로 비교했다. 다만 운영 인력의 진단 경험, 기존 Azure 관측 도구, 전환 비용을 종합해 실험 문서만 남기고 도입하지 않았다.

[03. 중복 전표 방지]
계근 callback에는 장비가 생성한 source_ticket_id가 있었다. consumer는 이 값을 owner 거점과 함께 inbox table의 unique key로 저장한 뒤에만 shipment 상태를 바꿨다. transaction이 끝난 뒤 같은 callback이 다시 도착하면 이미 처리된 inbox row를 확인하고 성공 응답만 반환했다. 단순 메모리 캐시가 아니라 SQL Server transaction을 최종 기준으로 삼았기 때문에 worker 재시작 뒤에도 중복을 막을 수 있었다.

[04. 가격 규칙 감사]
운임과 자재 단가는 적용 날짜, 고객 등급, 운송 거리로 결정됐다. 규칙 변경은 SQL Server system-versioned table에 남겼다. 운영자는 특정 전표가 만들어진 시점의 규칙을 재구성할 수 있었고, 잘못 배포된 단가표는 과거 row를 복사해 새 유효 구간으로 되돌렸다. 과거 row 자체를 수정하지는 않았다.

[05. 장비 장애 시 동작]
계근 제어기가 응답하지 않을 때 매 요청이 timeout까지 기다리면 API thread가 고갈됐다. 장비별 circuit breaker와 짧은 timeout을 적용하고, 최근 검증된 tare weight가 있는 경우에는 화면에 ‘임시 견적’임을 표시한 값을 돌려줬다. 실제 출하 확정은 장비가 회복되어 실측 callback이 들어온 뒤에만 가능했다. 이 경계 덕분에 정확하지 않은 값을 최종 전표로 저장하지 않으면서도 배차 상담은 계속할 수 있었다.

[06. 복구 훈련]
72시간 통신 단절을 모사해 46,200개 callback을 순서를 섞어 재생했다. inbox key 검증 결과 중복 shipment 생성은 0건이었다. 운영자는 DB row를 수동 수정하지 않았고 replay dashboard에서 거점별 처리량과 거절 사유만 확인했다. 동일 부하 조건에서 견적 API P95는 1.4초에서 380밀리초로 줄었다.

[07. 주변 경험]
별도 KilnWatch 프로젝트에서는 MQTT로 11,000개 소성로 센서 신호를 받고 InfluxDB에 보관했다. 이 경험은 QuarryFlow의 계근 전표 정합성과는 다른 관측용 workload다. 두 프로젝트를 하나의 성과로 합치지 않는다.

[08. 범위]
동적 가격을 추천하는 머신러닝 모델은 아이디어 회의만 있었고 설계·구현하지 않았다. 가격 규칙은 사람이 승인한 테이블이었다. 모바일 운전기사 앱도 다른 팀이 담당했다.

[09. 회고]
가장 중요한 결정은 메시지 제품보다 전표의 업무 식별자와 transaction 경계를 먼저 정의한 것이었다. topic filter는 격리와 확장에 도움을 줬지만, 중복 방지의 근거는 source_ticket_id와 owner 거점이 결합된 DB 제약이었다.
